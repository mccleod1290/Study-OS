Enumerating visible content d1

Mapping comes first. Work only on authorized targets. Start with the content you can see. You need a recording proxy and a crawler. Links and forms must exist. Step one. Browse every link. Finish every multistage form, through the proxy. Step two. Review the site map. The proxy parses every response. Step three. Open the rest by hand. Include what the spider found and you skipped. Step four. Repeat. A crawler helps. An HTML-only spider sees a JavaScript app as empty. The tool katana, with its J C flag, parses the JavaScript endpoints. A spider can also break sessions. It can call delete or admin functions. Exclude those links first. This does not apply to a client-routed page. It also fails on links inside dead compiled objects.

Discovering hidden content d2

Now find content that no link shows. You need three parts. A wordlist. A test that tells a real hit from the application's own error page. A source of removed pages. Start from the wordlist. Request each name with ffuf. Its A C flag calibrates the fake not-found filter. Read the status code and the size. A 200 can be a custom not-found page. Then the path is absent. A 401 or 403 means the path is closed, but present. Infer more names from what exists. AddDocument implies EditDocument. Add backup endings, such as dot bak and dot old. Archives add paths. A path in the archive that gives 404 now is a route the application once served. Search operators: site, quotes and minus still work. Link, related and cache do not. They fail silently. This does not apply when one URL picks its function by parameter.

Pages, functional paths, hidden parameters d3

Some applications use one URL for many functions. You need one URL that carries the function in a parameter, or a published API description. The condition is routing by value, not by path. In the book, a post to bank dot jsp names the servlet and the method in its parameters. Directory brute force finds nothing here. Map in two stages. GraphQL puts all calls on one URL. Introspection asks the server for its schema. Many servers disable it in production. An OpenAPI description lists the routes. Read the file openapi dot json. JavaScript bundles name routes that the interface never shows. The tool jsluice prints each URL it finds. Hidden parameters need their own search. The tool arjun, in stable mode, uses one thread and a delay. Param Miner tests up to 65,000 names per request. A plain file tree does not need this. A wordlist is enough there.

Entry points for user input d4

Next, list every place where input enters. The parts are URL path, query, body, cookies and trusted headers. The condition is that the input reaches server logic. In a REST-style path, the parts are data. Headers such as Referer, User-Agent and X-Forwarded-For are trusted. Fuzz each parameter name. A different response size shows a live name. JSON keys and nested fields are also entry points. The page marks this as not verified. Some input arrives out of band. Examples are SMTP mail, a server-side fetch, and a mobile API. For this, use an OAST server. OAST means out-of-band application testing. A server you control logs the lookups the target makes. The client prints a name. Send it in a header. The target resolves it, and the page shows nothing. The client prints the DNS hit. That proves the server resolved your value. A client-side-only field does not apply.

Fingerprinting server-side technology d5

Now name the technology behind the server. The parts are the Server header, error pages, and cookie and directory names. At least one must not be stripped. Read the banner. The tool curl, with the I flag, fetches the headers only. Server Apache 1.3.31 names the stack and the version. The tool httpx reads more signals. Its T D flag uses the Wappalyzer dataset. The status of httprecon and httprint is not verified. Extensions and error pages: asp, aspx, jsp, php and dll name a platform. Cookie and directory names are a fourth signal. JSESSIONID and PHPSESSID are examples. This signal is not verified. Name the stack. Apache-Coyote is Tomcat, a Java servlet container. Then find each third-party component and its version. Query OSV dot dev. An empty answer means no known entry. It does not mean no flaw. A CDN may normalize these signals. That is not verified.

Server-side functionality and unique behavior d6

Parameter names tell you what the server does. The parts are names that read like a programmer wrote them, and stay consistent. The condition is that the names carry meaning. Take calendar dot jsp, with isExpired equals zero, and OrderBy equals name. The file name points to Java. OrderBy points to a database ORDER BY. isExpired is a flag to flip. Now a REST path. Slash pub, slash media, slash 117, slash view maps to a hidden internal call. The call has a schema, an id and an action. Try edit and add as the action. Try higher ids. The tool ffuf can run the ids. Keep the rate low. Opaque tokens do not apply. The names must read like words.

Mapping the attack surface d7

Mapping ends before probing. No tool maps an application safely alone. Build the content map. Then build the functional map. Know the core functions and mechanisms. Session state. Access control. Authentication. Recovery. Match each feature to its usual bug class. The page lists upload, login, redirect and email. It marks this step not verified. Check third-party code. Use OSV dot dev. Use nuclei, with its A S flag, for known exposures. Then make the plan of attack. Rank the functions and the bug classes. First, probe all hosts with httpx. Only after the map, attack. Mix manual work with controlled automation.
