How this works

You answer first. The page never tells you the answer before you write. The struggle to say it is the learning. Four steps: explain, six questions, gap check, resurface prompts. Your text stays in this browser only.

Step 1. Teach it

Explain the talk to a smart friend who has not seen it. Do not summarise. Teach it: the core idea, why it matters, how to use it.

  • Mechanism gap: did you say why, not only what?
  • Prerequisite gap: did you use client, server, database, or durable without defining it?
  • Edge gap: did your story only work for the happy path?
  • Application gap: did you say what you do differently tomorrow?
  • Precision gap: did you use jargon you cannot define from first principles?

Step 2. Six questions

Each targets a different idea. Q1 is a tension. Q2 and Q4 use a case that is not in the talk. Q3 is a prediction.

Q1. Tension

He says the client must never talk to the database. Yet his Convex clients call backend functions directly and get live data. Reconcile the two. What is the real rule?

Good answer includes:
  • The rule is about unchecked paths, not about network hops
  • A public function is a path. Convex says public functions can be called by anyone [3]
  • Safety comes from an access check in the function, or a row rule such as RLS [2]
  • His 'read your API key' reason fits the secret key, not the publishable key [2]

Q2. New scenario

You build a support chat that sends AI replies. A user closes the tab mid-reply. Say what breaks in the naive build, what a durable process gives you, and what new risk the retry adds.

Good answer includes:
  • Naive: the work lives with the client request, so it dies with the tab
  • Durable: work lives on the server, survives, retries
  • New risk: a retry repeats a side effect (double charge, double send)
  • Control: an idempotency key, one token per action, so a repeat is harmless

Q3. Prediction

1000 users arrive overnight. By his design, what do you expect to fail or hurt first? He says only the plan needs an upgrade. Is that enough?

Good answer includes:
  • Likely first: cost (he already spent over $100 on a $20 plan) and third-party limits
  • Per-user sandbox boxes and inference calls are the heavy cost, not page serving
  • The money ledger (Postgres) is a place for contention and double spend
  • 'Can handle scale' is vendor reputation, not a test. A load test is missing

Q4. Apply the rule

An app has login, PDF export, a Stripe webhook handler, and a notification sender. Apply his footprint rule. Which blocks become services, and what would make you say no?

Good answer includes:
  • Count call sites. Few call sites and one job means a candidate
  • PDF export and the webhook handler are likely candidates. Login touches everything, so it stays
  • Say no when the team is one person and the split adds deploys and auth seams with no gain
  • He admits the rule is vibes, so you must state your own count and threshold

Q5. Defend

He installs integrations by pasting a component link to the agent. Threat-model this as a defender. Name two risks and one control for each.

Good answer includes:
  • Risk: third-party code runs inside the backend. Control: pin the version, read the diff
  • Risk: the agent holds keys while installing. Control: least-privilege keys, scoped per integration
  • Risk: a link swap or a lookalike package. Control: allowlist sources, install from the official component page only
  • Do not call this an attack walkthrough. It is a review checklist

Q6. Disagree

Give the strongest case against his core message. Then say what evidence would change your mind.

Good answer includes:
  • Abstraction layers move failure to a vendor, they do not remove it
  • Lock-in, price change, outage, with no exit plan
  • Evidence that would convince: a load test, a cost per user, a vendor-exit drill, an access-control review
  • Do not settle for 'it depends'. Name the number

Checked: 0 of 6. Fewer than 4 means re-read the matching sections of the breakdown and the concept map, then answer again.
