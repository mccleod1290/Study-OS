Tensions

T1. Abstraction against control

Abstraction pushes toward speed and less ops work.
Control pushes toward price, exit, and failure you can see.

Why both hold. At 10 users speed wins. At 10,000 you must know what a request costs.

Boundary. Before launch, take the layer. After first revenue, measure cost per user.

What breaks. Pick only abstraction: a bill you cannot explain. Pick only control: a six-month infra project before a first user. He chose abstraction and says cost is a later problem (27:07). 3

[1]

T2. 'Client never talks to the DB' against reactive client queries

The rule pushes toward no direct path.
Convex pushes toward clients call public functions and get live data.

Why both hold. The rule is about unchecked paths. A public function is a path. It is safe only if it checks who is calling.

Boundary. The boundary is a function with an access check, or a row rule (RLS). Not a network hop.

What breaks. Teach the rule as 'no hop' and you miss a public function with no check. 5

[2] [3]

T3. One backend against separate services

One box (Convex) pushes toward cheaper, simpler.
Services pushes toward own owner, own failure, own scale.

Why both hold. He says himself: to save money, put everything in Convex (27:30). He splits anyway, for the future team.

Boundary. Split by footprint and by who will own it. Not before.

What breaks. Split too early: more seams, more deploys, more auth to check. Split too late: one giant backend nobody dares touch. 3

[1]

T4. One repo for the agent against blast radius

Monorepo pushes toward the agent sees all.
Isolation pushes toward limits what one change or one leak touches.

Why both hold. One repo gives context. Separate deploys and data stores give isolation. He keeps one repo and separate deploys.

Boundary. Share code and context. Separate secrets and data stores per service.

What breaks. One repo with shared secrets: one leak opens every service. Inference.2

Learning order

  1. Foundation. Trade-off, quality axes, client, server, database, abstraction.
  2. Mechanisms. Server-mediated access, unified backend, durable process, queue, component, monorepo.
  3. Applied. Control plane, footprint rule, Effect on money paths, credits billing, observability.
  4. Judgment. Accepted trade-off, vibes against formula, unmeasured scale, vendor dependence.

Map description

At the centre sits the control plane (Convex). Around it: the clients on one side, the services on the other, the components above. Monorepo and agent experience are the two long links: they tie the whole picture to one reader, the agent. The surprise is that security is almost absent. The access-control edge in T2 is the missing wire between "client" and "database". The mind map file draws this.
